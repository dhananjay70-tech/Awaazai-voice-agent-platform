## 2. Implement a streaming endpoint

Add a new endpoint:

`POST /chat/stream`

Use Server-Sent Events (SSE) over HTTP if supported cleanly by the existing FastAPI architecture.

Example request:

{
  "message": "Explain AI agents in simple Hinglish.",
  "session_id": "stream-demo-001",
  "language": "hinglish"
}

The response must stream events progressively instead of waiting for the entire Gemini response.

Use a documented event format such as:

- `start`: session/request metadata
- `token`: a generated text chunk
- `done`: completion metadata
- `error`: a safe error code and request ID

Example SSE event format:

event: start
data: {"session_id":"stream-demo-001","model":"configured-model"}

event: token
data: {"text":"AI agents"}

event: token
data: {"text":" can perform tasks..."}

event: done
data: {"session_id":"stream-demo-001"}

These are illustrative events; implement a consistent format and document the actual contract.

Requirements:
- Use the existing Gemini provider abstraction and configured model.
- Use the actual supported streaming API from the installed `google-genai` version.
- Send chunks as soon as they become available.
- Do not buffer the entire generated answer before emitting token events.
- Set the appropriate SSE content type and anti-buffering headers where applicable.
- Ensure the existing security headers and request ID behavior are preserved.
- Keep `/health` and `POST /chat` working unchanged.
- Validate message, session ID, and language using the existing schemas where appropriate.
- Keep system instructions and language behavior consistent with Phase 2.

## 3. Preserve conversation history correctly

Integrate streaming with the existing bounded in-memory session manager.

Requirements:
- Use the same session when the client sends an existing `session_id`.
- Maintain isolation between sessions.
- Ensure concurrent requests for the same session cannot corrupt history.
- Do not add a partial or failed assistant response to history.
- Only commit the completed assistant response after successful generation.
- Handle empty provider output safely.
- Reuse existing history limits, expiration, and eviction policies.
- Do not introduce a second independent session store.

Inspect the existing locking design carefully. Do not hold a session lock indefinitely if a client disconnects or Gemini hangs.

## 4. Cancellation and cleanup

Handle HTTP client disconnects and generator cancellation correctly.

Requirements:
- If a client disconnects while receiving the stream, cancel the upstream Gemini generation when supported by the SDK.
- Release session locks and other resources in all success, error, timeout, and cancellation paths.
- Do not leave background tasks running unnecessarily.
- Apply a configurable generation timeout.
- Avoid unbounded buffering or unbounded concurrent generations.
- If the SDK does not support true upstream cancellation, document the limitation honestly and implement the safest available cleanup.
- Do not claim cancellation works unless it has been verified.

## 5. Measure latency

Add lightweight, privacy-safe timing measurements for:

- Whether generation completed, failed, timed out, or was cancelled

Requirements:
- Use a monotonic clock for duration measurements.
- Never log prompts, response text, API keys, or session IDs.
- Keep metrics bounded and avoid adding a new metrics platform.
- Include useful timing metadata in the final `done` event if appropriate.
- Do not expose sensitive internal details to clients.

## 6. Error handling

Reuse Phase 2's standardized error model and existing error codes wherever possible.

Handle:
- Missing Gemini API key
- Unavailable or retired model
- Provider authentication failure
- Quota/rate-limit exhaustion
- Provider timeout
- Network errors
- Empty/malformed streaming chunks
- Unexpected provider failures
- Client disconnect or cancellation
- Invalid request body

Before the SSE response begins, use the appropriate HTTP status code if the request cannot start. After streaming has started, send a safe SSE `error` event when possible, then terminate the stream.

Never send a fake successful reply. Never include API keys, stack traces, raw provider errors, or user prompts in error events.

## 7. Concurrency and resource limits

Review the existing session locking and provider call architecture before implementation.

Requirements:
- Same-session conversations must be serialized safely.
- Different sessions should be able to progress concurrently within a reasonable configured limit.
- Bound the number of concurrent Gemini generations.
- Prevent session-lock leaks, semaphore leaks, and task leaks.
- Avoid blocking the FastAPI event loop.
- Use the installed SDK's supported async streaming interface where available.
- Keep resource limits configurable with safe defaults.
