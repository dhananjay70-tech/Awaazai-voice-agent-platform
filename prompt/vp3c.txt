## 1. Choose and verify the TTS provider

Use Deepgram's documented Text-to-Speech API, preferably its streaming HTTP endpoint, if supported by the current service architecture.

Before implementing:
- Inspect the installed `websockets` and HTTP client versions.
- Verify the official Deepgram TTS endpoint, supported request format, available voice models, and audio output format from current official documentation.
- Reuse existing dependencies wherever possible.
- Keep TTS separate from STT and Gemini provider code.

Do not assume a particular voice model supports Hindi or Hinglish without checking the current documentation. Select a documented voice/model and make it configurable.

If `DEEPGRAM_API_KEY` is already configured for STT, reuse the same environment variable. Do not add duplicate credentials unnecessarily. If missing, the service must start and report a safe `tts_not_configured` error when TTS is requested.

## 2. Implement a streaming TTS endpoint

Add a new endpoint, preferably:

`POST /tts/stream`

Request example:

{
  "text": "Namaste! Main AwaazAI hoon. Aapki kya help kar sakta hoon?",
  "language": "hinglish",
  "voice": "configured-default"
}

Adapt field names to existing schema conventions if needed.

The endpoint must:
- Validate non-empty text and enforce a maximum text length.
- Validate the supported language values: English, Hindi, and Hinglish.
- Send text to the real Deepgram TTS provider.
- Stream audio bytes progressively instead of buffering the complete audio before responding.
- Use the documented audio MIME type and format.
- Return correct HTTP status codes before streaming starts.
- Use appropriate streaming headers to prevent intermediary buffering where applicable.
- Preserve request IDs and applicable security headers.
- Never return fake audio or a fabricated success response.

Choose and document a suitable audio format for browser playback. Prefer a format the chosen Deepgram model actually supports, and do not label raw PCM as MP3 or vice versa.

## 3. Resource and concurrency safety

Follow the existing `app/limits.py` architecture where practical.

Implement:
- A configurable concurrent TTS request limit.
- A configurable provider timeout.
- Maximum text length.
- Cancellation when the HTTP client disconnects.
- Cleanup of upstream HTTP connections and generation slots on success, error, timeout, or cancellation.
- No unbounded audio buffering.
- No unnecessary background tasks.
- Safe behavior when the provider returns empty audio or malformed responses.

Do not interfere with the existing Gemini generation limit or STT concurrency limit.
